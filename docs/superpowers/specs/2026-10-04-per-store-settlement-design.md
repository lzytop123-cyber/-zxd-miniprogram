# 按门店分结算对公账户设计

日期：2026-10-04  
状态：已确认并实现首版

## 背景与目标

同一公司主体经营两家门店。公司再开第二个对公账户：

- **老店**：小程序微信支付、美团/抖音核销结算 → **现有对公**（现有微信商户 / 现有美团门店）
- **新店**：小程序微信支付、美团/抖音核销结算 → **新对公**（新微信商户号结算到新对公；新美团/抖音门店结算到新对公）

顾客仍使用同一个小程序、同一 AppID，按门店选店、预约、购卡、验券。两店权益互不通用。

本设计不引入「两家经营公司」权限隔离；后台仍可共用。重点是 **收款商户按门店分流** 与 **本店权益仅本店可用**。

## 非目标（首版不做）

- 分店管理员只能看本店的账号隔离
- 按门店拆分余额钱包（全局充值余额仍属公司钱包；见下文支付限制）
- 自定义座位图上传
- 商家自助入驻、分账 API、订阅收费

## 方案选择

采用 **收款账户（PayAccount）实体 + 门店绑定**：

- 每个收款账户对应一套微信支付商户配置（mchid、证书路径、APIv3 key 等），在微信侧结算到指定对公账户
- 门店通过 `pay_account_id` 绑定收款账户；未绑定则使用全局 `.env` 默认商户（兼容现网老店）
- 预约微信支付订单、购卡订单在创建支付时 **快照 `pay_mchid`**，查单/退款/回调验签均按快照选择客户端，禁止回退到其他店商户

备选「仅 env 写死店2商户」运维差、扩展差，不采用。  
备选「商户字段全堆在 Store 表」不利于密钥管理与复用，不采用。

美团/抖音资金不经过小程序微信商户，结算在平台商家侧完成。系统侧保证：每店独立 `meituan_shop_id`（及必要 token）、独立 deal 映射；核销发出的期限卡必须带本店 `store_id`。

## 数据模型

### `pay_accounts`

| 字段 | 说明 |
|------|------|
| id | 主键 |
| name | 展示名，如「公司对公A」「公司对公B」 |
| mchid | 微信商户号 |
| serial_no | 证书序列号 |
| api_v3_key | APIv3 密钥（仅服务端；接口永不回显明文） |
| cert_path / key_path | 商户证书与私钥路径（相对 backend 或绝对路径） |
| public_key_id / public_key_path | 可选，公钥模式 |
| status | 1 启用 / 0 停用 |
| created_at | 创建时间 |

全局 `.env` 中的 `WX_PAY_*` 视为隐式「默认账户」，不必强制迁移入库；老店 `pay_account_id` 为空时走默认账户。

### `stores` 新增

| 字段 | 说明 |
|------|------|
| pay_account_id | 可空，FK → pay_accounts |
| benefits_isolated | 整数，默认 0；为 1 时该店预约/购卡路径禁用余额支付，且强制本店卡券隔离（新店设为 1） |

现有 `meituan_shop_id` / `meituan_auth_token` 继续按店配置。

### 订单快照

- `reservations.pay_mchid`：可空；微信支付下单成功或发起支付时写入
- `card_purchase_orders.pay_mchid`：同上

历史订单 `pay_mchid` 为空时，退款/查单回退全局默认商户（仅兼容旧数据）。

## 支付与核销行为

### 解析收款账户

`resolve_pay_account(store) → PayAccount | DefaultEnvAccount`：

1. 若 `store.pay_account_id` 指向启用中的账户 → 用该账户
2. 否则 → 全局 `.env` 默认商户
3. 若绑定账户停用或证书不全 → **拒绝支付**，错误信息明确，**禁止**改用默认商户

### 微信下单 / 查单 / 退款 / 回调

- `WechatPayService` 按账户缓存多个客户端（按 mchid），不再假设全局单例唯一
- `create_jsapi_order(..., pay_account=...)` 写入订单 `pay_mchid`
- `query_order` / `refund` 读取订单 `pay_mchid` 选客户端；缺失则默认账户
- 支付回调：先用通知中的商户信息或遍历已知账户验签；验签成功后核对订单 `pay_mchid` 与金额；不一致则不入账并告警

开发环境：`APP_ENV=development` 或默认商户未配置时保持 mock；若门店绑定了账户且配置齐全，可用真实账户（测试以本地开关为准，默认仍 mock 除非显式配置）。

### 适用订单类型

| 类型 | 按店商户 |
|------|----------|
| 预约微信支付 | 是（按 `reservation.store_id`） |
| 在线购买期限卡/套餐 | 是（按 `CardPurchaseOrder.store_id`） |
| 余额充值 | 否，仍走默认商户（全局钱包） |
| 学习报告等非门店商品 | 否，默认商户 |

### 权益隔离（两店各是各的）

1. **期限卡**：兑换与购卡发放时必须写入 `period_cards.store_id`。预约使用时：若卡有 `store_id` 且与预约门店不同 → 拒绝。新店与老店新发放的卡均带店。历史 `store_id` 为空的卡：仅允许在「未开启 benefits_isolated」的门店使用（兼容老店）；在 `benefits_isolated=1` 的新店不可使用空 store 卡。
2. **优惠券**：若券已绑定门店则同规则；未绑店的全局券不得用于 `benefits_isolated=1` 的门店。
3. **余额**：`benefits_isolated=1` 的门店预约/购卡 **禁止余额支付**，仅微信支付（及本店期限卡若来源为本店团购/购卡）。
4. **团购核销**：必须带 `store_id`；使用该店美团/抖音配置与映射；发卡绑定该店。跨店券码不得核销到错误门店。

小程序：在 `benefits_isolated` 门店的下单页隐藏余额/不适用的卡券入口；服务端仍做强制校验。

## 管理后台

- 门店编辑：选择收款账户、`benefits_isolated`、美团门店 ID 等
- 收款账户列表：新建/停用；创建时写入密钥与路径；编辑时密钥留空表示不修改；列表与详情 **不返回** api_v3_key 明文
- 不在此阶段做「店员只能看本店」

## 配置与上线顺序（运营）

1. 银行开立新对公账户  
2. 微信：申请/配置第二商户号，结算户绑新对公，完成与小程序 AppID 绑定  
3. 美团/抖音：新店门店结算绑新对公，取得 shop/poi 与映射  
4. 后台：创建收款账户 → 新店绑定 → `benefits_isolated=1` → 配置美团信息与 deal 映射 → 补座位与价格  
5. 开发/预发：两店分别小额支付、退款、团购核销；确认商户号与对账单一致  
6. 再对顾客开放新店营业

## 验收标准

1. 老店微信预约/购卡 → 默认（老）商户；新店 → 新商户；两笔退款各回原商户  
2. 新店未绑定可用收款账户时，微信下单失败且不落到老商户  
3. 新店不能用余额；不能用老店期限卡/不适用券  
4. 新店团购核销发卡的 `store_id` 为新店，无法在老店预约抵扣  
5. 错商户回调或金额不符不入账  
6. 现有老店在未改绑前行为与现网一致  

## 测试要点

- 单元/接口：账户解析、隔离拒绝、快照 mchid、退款选客户端、回调校验  
- Mock 模式：可注入两个假 mchid 验证路由  
- 人工：证书齐全时真机小额支付与原路退款（可选）

## 风险

- 第二商户与小程序异主体/同主体绑定未完成前，新店不可开放真支付  
- 美团是否允许同公司两店两结算户取决于平台审核，属运营前置，不在代码内解决  
- 回调 URL 仍为统一 `BASE_URL/api/payment/wechat/notify`，依赖多客户端验签与订单 mchid 校验
