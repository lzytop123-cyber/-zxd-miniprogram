# 两门店系统安全与功能审查

审查日期：2026-11-08（北京时间）。对象：F:/zxd-pro 当前工作区，包含尚未提交的代码。

## 结论

确认 **12 类缺陷（8 项高优先级 P1、4 项中优先级 P2）**，用 **15 个隔离场景**复现。当前多店支持在门店列表和部分后台接口上已经存在，但财务台账、优惠券、卡扣减及支付状态处理仍有缺口。建议先处理资金与跨店权限问题，再完善营业规则和门禁履约。

这不是线上入侵或损失认定。本次没有访问生产服务器，没有操作真实微信支付、团购核销或门锁，没有写入业务数据库，也没有修改业务代码。已确认的是当前代码在给定条件下会发生的错误行为。

## 已复现问题

### A01 · P1 · 店长可跨店查看和登记财务台账

- 代码：[待核对列表](F:/zxd-pro/backend/app/api/routes/admin_receipts.py:135)、[人工确认](F:/zxd-pro/backend/app/api/routes/admin_receipts.py:184)、[退款登记](F:/zxd-pro/backend/app/api/routes/admin_receipts.py:322)。
- 原因：部分普通列表调用了 scope_store_id，但平台待核对列表直接返回全站 candidates；确认核销和退款登记按 ID 取记录，未校验门店。
- 复现：店 A 店长，使用默认 receipts 权限，通过真实 FastAPI 路由和 AdminRoleGuardMiddleware，读取店 B 待核对记录；随后给店 B 记录登记收款和退款，均返回 HTTP 200。
- 影响：不同店长能看到、改变另一店的财务台账。这里的“退款登记”只修改账本，不会调用微信实际退钱接口。
- 建议：对列表、单条读取、确认、日期修改、退款登记、批量核对统一执行服务端门店校验，不能只依赖列表过滤。批量入口也要使用同一范围。
- 证据：test_14。

### A02 · P1 · 开门记录可绕过门店隔离

- 代码：[开门记录筛选](F:/zxd-pro/backend/app/api/routes/ble.py:258)。
- 原因：传入 lock_id 时进入第一个分支，本店过滤放在 elif 中，因此不会叠加执行。
- 复现：店 A 店长不传锁 ID 时看不到店 B 数据；传店 B 锁 ID 后 HTTP 200，返回店 B 开门记录及顾客手机号。
- 建议：先验证门锁归属，并始终叠加本店过滤。
- 证据：test_01（包含真实 HTTP 路由及权限中间件）。

### A03 · P1 · 微信退款失败仍标记“已退款”

- 代码：[用户取消](F:/zxd-pro/backend/app/api/routes/reservation.py:708)、[后台取消](F:/zxd-pro/backend/app/api/routes/admin.py:1349)、[退款返回值](F:/zxd-pro/backend/app/services/wechat_pay.py:347)。
- 原因：WechatPayService.refund 失败返回 False；两个取消入口均忽略该结果，仍把 pay_status 置为 2。用户入口还填写 refunded_at。
- 复现：模拟微信退款返回 False，两个入口都保存为“已取消、已退款”。
- 影响：顾客实际未收到退款，系统却显示已退，人工排查与补退容易遗漏。与座位冲突退款路径的严格确认处理不一致。
- 建议：建立退款中、退款成功、退款失败状态；只在确认成功后标记已退款，使用稳定退款请求号，并提供重试与核对入口。
- 证据：test_02、test_03。

### A04 · P1 · 优惠券可重复打折，也能绕过新店权益隔离

- 代码：[创建预约](F:/zxd-pro/backend/app/api/routes/reservation.py:275)、[支付时隔离检查](F:/zxd-pro/backend/app/api/routes/reservation.py:352)、[核销调用](F:/zxd-pro/backend/app/api/routes/reservation.py:422)、[优惠券核销](F:/zxd-pro/backend/app/services/coupon_service.py:35)。
- 原因：下单时保存折后价，却不保存所用券 ID；支付时只看本次请求带不带 coupon_id。核销失败的返回值也未作为履约条件。
- 复现一：同一张 5 元券给两店各 10 元订单下单；支付请求不再携带券 ID，两笔都只扣 5 元，券仍是未使用。
- 复现二：店 B 开启 benefits_isolated=1，下单带券、微信预支付时不带券，服务端仍向支付服务传入折后 5 元金额。
- 建议：订单保存券归属及折扣依据；预览、下单均校验门店；用券占用、核销及订单支付状态须事务一致。支付阶段从订单读取权益，不能依赖客户端重复声明。
- 证据：test_04、test_05；微信调用已模拟，未发起真实支付。

### A05 · P1 · 周/月/季预约可任意拉长，却只收一份套餐价

- 代码：[时段计算](F:/zxd-pro/backend/app/services/booking.py:101)、[套餐计价](F:/zxd-pro/backend/app/services/business.py:467)。
- 原因：客户端提交 end_time 时直接采用该结束日期，未按定价 valid_days 限制跨度；周/月/季价格又是固定 rule.price。使用期限卡的路径另有校验，余额或微信支付路径没有相同限制。
- 复现：设置 30 天月卡价格 100 元，提交 365 天预约，订单仍收 100 元并能用余额支付成功。
- 影响：可低价长期占用座位。
- 建议：由服务端依据套餐规则确定结束日期，或校验天数并按购买数量计费；所有支付方式使用一致规则。
- 证据：test_06。

### A06 · P1 · 同一张卡可被并发重复消耗

- 代码：[读卡与座位锁](F:/zxd-pro/backend/app/api/routes/reservation.py:370)、[卡扣减](F:/zxd-pro/backend/app/services/card_service.py:547)。
- 原因：只按座位加锁，不按卡加锁；卡通过普通 ORM 对象先读取后计算扣减，缺少卡行锁、条件更新和版本冲突检查。两个不同座位、不同门店使用的是不同锁。
- 复现：两个请求会话先读到同一张通用小时卡剩余 1 小时，各支付两店的一小时预约；两笔订单都成功，卡只剩 0 小时。
- 建议：事务内锁定卡并重读，或用剩余额度和状态条件原子扣减，确保失败请求不能履约。
- 证据：test_09。

### A07 · P1 · 充值履约不是数据库层面的幂等

- 代码：[充值履约](F:/zxd-pro/backend/app/services/booking.py:492)、[支付通知](F:/zxd-pro/backend/app/api/routes/payment.py:157)。
- 原因：仅检查当前内存对象的 pay_status，没有锁定或原子抢占充值订单；钱包余额原子增加只能防止丢失更新，不能防止同笔充值重复入账。
- 复现：两个会话先读到同一笔未支付充值单，各履约并提交，10 元充值增加 20 元，产生两条同订单充值流水。
- 建议：数据库原子变更“未支付→已支付”，只有成功变更的请求可加余额；流水增加订单与业务类型唯一约束，放在同一事务。
- 证据：test_10。

### A08 · P1 · 余额预约可重复扣款，也可重复退款

- 代码：[余额支付](F:/zxd-pro/backend/app/api/routes/reservation.py:406)、[取消与余额退款](F:/zxd-pro/backend/app/api/routes/reservation.py:693)。
- 原因：支付状态检查在锁外；锁内不重新锁定、刷新订单并核验已支付状态。取消入口也缺少订单原子状态转换。
- 复现：两个请求会话预读同一订单后交错提交，10 元订单扣款两次；两个取消请求预读同一已付款订单后交错提交，则退款两次，余额比购买前多 10 元。
- 建议：以订单行为单位执行锁定或条件状态转换，消费/退款流水增加幂等约束。支付、取消、回调采用统一状态机。
- 证据：test_12、test_13。

### A09 · P2 · 停业和营业日历休息日没有约束预约

- 代码：[预约准备](F:/zxd-pro/backend/app/api/routes/reservation.py:69)、[座位校验](F:/zxd-pro/backend/app/services/booking.py:167)、[座位可售判断](F:/zxd-pro/backend/app/services/store_seat_maps.py:278)。
- 原因：预约校验门店存在、座位可售和时段冲突，却未校验 Store.status 或 StoreCalendarDay.is_closed。门店从列表隐藏不能阻止使用旧链接或直接请求预约。
- 复现：门店设为停业，同时预约日设为休息日，仍能创建并支付预约。
- 建议：下单和支付前检查门店状态及营业日历；跨日订单检查覆盖的每个营业日。
- 证据：test_07。

### A10 · P2 · 两店独立营业时间设置没有参与预约校验

- 代码：[全局写死营业时间](F:/zxd-pro/backend/app/services/store_hours.py:5)、[时段校验](F:/zxd-pro/backend/app/services/store_hours.py:44)。
- 原因：后端统一使用 07:30–23:30，未从订单门店及日历读取实际营业时间。
- 复现：门店配置 12:00–18:00，仍允许预约当日 10:00–11:00。
- 建议：统一解析“门店默认时间 + 当天例外”的营业窗口，让选座、下单、支付、入座和门禁使用同一规则，并定义 00:00–00:00 的业务含义。
- 证据：test_08。

### A11 · P2 · 支付成功但发钥匙失败后缺少恢复路径

- 代码：[先提交支付成功](F:/zxd-pro/backend/app/api/routes/payment.py:111)、[发钥匙失败后跳过](F:/zxd-pro/backend/app/services/business.py:497)、[主动确认提前返回](F:/zxd-pro/backend/app/api/routes/reservation.py:472)。
- 前提：门锁没有可用备用 lock_data，TTLock 临时发钥匙失败。
- 复现：支付处理返回 paid，订单已支付，但 BleKey 数量为 0；再次确认支付不会重试发钥匙，可开门时间内取钥匙返回 404。
- 影响：顾客已付款但无法开门，必须人工处理。
- 建议：持久化门禁履约状态，提供幂等重试、后台补发和失败提醒。支付成功不代表发钥匙成功。
- 证据：test_11；未测试真实通通锁硬件。

### A12 · P2 · 店长手工登记收款后，本店列表和统计看不到

- 代码：[手工登记](F:/zxd-pro/backend/app/api/routes/admin_receipts.py:287)、[按门店筛台账](F:/zxd-pro/backend/app/services/receipts.py:66)、[台账模型](F:/zxd-pro/backend/app/models/receipts.py:11)。
- 原因：Receipt 没有 store_id，靠来源订单反查归属；manual: 来源既无关联订单，也没有其他门店归属字段。
- 复现：店长登记 20 元转账收款返回 HTTP 200；再查本店收款列表，total=0，但数据库实际保存了 1 条记录。
- 建议：收款记录保存不可变门店归属，店长登记时由服务端绑定本店；总部登记时明确选择门店，迁移历史手工流水。
- 证据：test_15（真实 HTTP 路由及权限中间件）。

## 建议处理顺序

1. 先补全跨店财务与门锁日志授权（A01、A02）；同时处理退款假成功（A03）。
2. 修复计费和权益校验（A04、A05），以及订单、充值、卡扣减的数据库事务与幂等（A06–A08）。
3. 补齐营业日历、独立营业时间、门禁失败恢复和手工收款归属（A09–A12）。
4. 在隔离环境回归两店预约、余额/卡券、各自店长权限、取消退款，再核对线上配置与真实小额收款退款。上线前将复现脚本的断言改成安全行为断言，作为回归用例。
